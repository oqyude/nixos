# ADR-0007: 3x-ui — пин `v3.10.2` → `v3.11.0` (ядро 26.10.10 → 26.10.21)

**Статус:** accepted и развёрнут 2026-10-27 на **sapphira** и **otreca**: панель 3.11.0, ядро **Xray 26.10.21** (отозванный 26.10.10 больше не используется), панель отвечает 200, REALITY проверен владельцем с клиента.

**Дата:** 2026-10-25

**Контекст.**

Панель 3x-ui запинена на `ghcr.io/mhsanaei/3x-ui:v3.10.2` с 2026-10-20
(инцидент 2026-10-14, R1.5): до этого был `:latest`, и релиз панели молча
притащил ядро Xray **26.10.10** вместо 26.7.x. Ядро ≥ 26.9.8 требует в
REALITY ClientHello key share `X25519MLKEM768`, который отдают только
uTLS-отпечатки `chrome`/`firefox`/`safari`; с `qq`/`edge` отказ **молчаливый**
— TCP соединяется, TLS «успешен», трафика нет (R1.16). Тогда это выглядело как
«сломалась вся панель», а лечилось `fp` и `minClientVer` на живых хостах.

Пин `v3.10.2` закрыл тихий дрейф, но сам по себе оказался не нейтральным:
**апстрим отозвал бандл 26.10.10.** В release notes `v3.11.0` (опубликован
2026-10-25) прямо сказано, что «the pulled v26.10.10 binary pins are
replaced». То есть зафиксированная версия тянула именно то ядро, от которого
апстрим отказался, — это второй, независимый от «хочу свежее» аргумент за
обновление.

Состояние ядра на хостах (R1.8: ядро — состояние БД панели, не Nix), на
2026-10-20:

| Хост | Панель | Ядро | Источник |
|---|---|---|---|
| sapphira | 3.10.2 | **26.10.10** | дефолт бандла v3.10.2 (руками не выбиралось) |
| otreca | 3.10.2 | **26.7.28** | выбрано руками в UI |

**Решение.**

`modules/containers/3x-ui.nix:71` — `image = "ghcr.io/mhsanaei/3x-ui:v3.11.0"`.
Пин остаётся **явным тегом**: `:latest` не возвращается ни при каких условиях
(это и был вектор дрейфа), обновление — только с записью в
`.agent/decisions/` (R1.5).

**Обоснование.**

- **Отозванный бандл.** Держать пин на версии, чей бандл апстрим объявил
  отозванным, — значит сознательно оставаться на нерекомендованном ядре.
- **Смена ядра всё равно неизбежна.** 26.10.10 уже стоит на sapphira; переход
  на поддерживаемый 26.10.21 не добавляет нового класса риска (REALITY-условия
  `fp`/`minClientVer` те же, R1.16), а убирает отозванный артефакт.
- **Один хост отстаёт сильнее.** На otreca ядро 26.7.28 выбрано руками и
  образом не меняется; обновление панели не форсирует ядро (см. риски).

**Альтернативы и почему не выбраны.**

1. **Оставить `v3.10.2`.** Ноль работ, но пин тянет отозванное ядро, и любой
   будущий rebuild/пересоздание контейнера возвращает 26.10.10.
2. **`:latest`.** Отклонено (R1.5): ровно этот путь дал аварию 2026-10-14.
3. **`v3.11.0` + принудительный откат ядра на 26.7.28 в UI.** Отклонено:
   26.7.28 — то же неподдерживаемое состояние, а на sapphira потребовало бы
   отдельной ручной операции в панели без выигрыша.
4. **Собрать/запинить конкретный digest образа.** Дало бы иммутабельность, но
   усложняет обновление и не даёт ничего поверх явного тега при текущей
   модели эксплуатации.

**Последствия.**

- **REALITY.** Ядро 26.10.21 — та же ветка ≥ 26.9.8 ⇒ `fingerprint` = `chrome`
  (или `firefox`/`safari`) и `minClientVer = 1.0.0` обязательны на всех
  инбаундах; с `qq`/`edge` отказ молчаливый (R1.16). Новых требований
  v3.11.0 не вводит.
- **Ядро не обновляется «само» от образа.** Версия ядра живёт в БД панели
  (R1.8): после первого старта панель может сохранить ранее выбранное ядро.
  Если в Panel Settings → Xray version осталось 26.10.10 — выбрать 26.10.21,
  затем `POST /panel/api/server/restartXrayService` (R1.18) и переподписать
  клиентов; иначе UI и файл `config.json` разойдутся.
- **Пересоздание контейнера.** Новый образ = новое создание `3xui_app`, порты
  применяются только при пересоздании (R1.11): после rebuild проверить
  `podman inspect 3xui_app --format '{{json .NetworkSettings.Ports}}'`
  (2049, 2096, 8443; на otreca ещё `127.0.0.1:15380→443`).
- **Миграции БД панели.** v3.11.0 несёт миграции схемы: первый старт меняет
  базу в томе `db/` **необратимо**. Это главный риск и причина, по которой
  откат — не одна строка обратно.
- **Окно недоступности REALITY.** Пересоздание контейнера = ретрай-флуд
  клиентов; `worker_connections = 512` в nginx VDS — известный узкий мест
  (ADR-0003). Планировать в нерабочее время.
- **Доки обновлены:** `AGENTS.md` (инв. 5 + ловушка), R1.5/R1.8 в
  `project-rules.md`, `project-state.md`, `manifest.md` (T43), комментарии
  `.ci/checks.sh`. Хроника в `notes/3x-ui-xray-26.9.md` не переписана — там
  `v3.10.2` остаётся фактом того инцидента, добавлена ссылка на этот ADR.

**Откат.**

Откат на `v3.10.2` **невозможен одной правкой строки**: после первого старта
v3.11.0 база мигрирована, старый образ её не поймёт. Порядок:

1. `image` → `v3.10.2`, `nixos-rebuild switch` (или `boot` + reboot).
2. Восстановить `db/` из бэкапа, снятого **до** первого старта v3.11.0.
   - sapphira: `/home/oqyude/External/Services/nodes/sapphira/3x-ui/db/`
     (= `/mnt/services/nodes/sapphira/3x-ui/db/`, bind-mount на External);
   - otreca: `/mnt/services/nodes/otreca/3x-ui/db/` (корневая ФС, External нет).
3. Пересоздать контейнер и проверить панель/ядро.

Без шага 2 откат даст панель, которая либо не стартует, либо читает
полумигрированную схему.

**Проверка после `nixos-rebuild switch` (владелец).**

1. **До rebuild:** `install -d` бэкап-каталога и `cp -a` тома `db/`
   (см. пути выше). Убедиться, что бэкап читается (`sqlite3 x-ui.db 'pragma
   integrity_check;'` при наличии sqlite3).
2. **После старта:** в панели ядро = **26.10.21** (иначе выбрать вручную +
   `restartXrayService`, R1.18).
3. **Панель:** `https://pubray1.zeroq.su/pubray/` открывается (TLS терминирует
   сама панель, nginx делает только `ssl_preread`; `GET /` → 404 — норма).
4. **REALITY:** живая ссылка с клиента при `fp=chrome` (или `firefox`/
   `safari`) и `minClientVer=1.0.0` → HTTP 204 через прокси,
   `uConn.Verified: true`. С `qq`/`edge` проверять бессмысленно — отказ
   молчаливый (R1.16).
5. **Порты:** `podman inspect 3xui_app --format '{{json .NetworkSettings.Ports}}'`
   — 2049/2096/8443, на otreca ещё 15380→443.
6. **При поломке REALITY:** откат по разделу «Откат» выше (строка + rebuild +
   восстановление БД).

**Связанное:** ADR-0003 (цепочка REALITY), R1.5, R1.8, R1.11, R1.16, R1.18,
T6–T10, `.agent/decisions/notes/3x-ui-xray-26.9.md`.

## Deployment record (2026-10-27)

| | sapphira | otreca |
|---|---|---|
| доступ | локально | `ssh otreca-tailscale` (100.64.1.0); прямой 109.248.161.5 не отвечает |
| бэкап `db/` до первого старта | `~/backups/3xui-db-pre-3.11.0-20261026T*.tar.gz` (1.3 МБ) | `~/backups/3xui-db-pre-3.11.0-20261026T221450Z.tar.gz` (980 КБ) |
| активация | `nixos-rebuild switch --flake .#sapphira` | `nixos-rebuild switch --flake .#otreca --target-host oqyude@100.64.1.0 --use-remote-sudo` |
| панель / ядро после | 3.11.0 / Xray 26.10.21 | 3.11.0 / Xray 26.10.21 |

Две грабли, обе записаны в журнал директора:

1. **Образ тянется на активации.** `podman pull ghcr.io/mhsanaei/3x-ui:v3.11.0` заранее — иначе
   `podman-3x-ui_app.service` стартует в момент активации и ждёт сеть (а при сбое pull панель
   остаётся лежать).
2. **`nixos-rebuild` под локальным `sudo` не видит ssh-алиасов.** Первый заход на otreca упал с
   `Could not resolve hostname otreca-tailscale: Name or service not known`: копирование делает
   `nix-copy-closure` **от root**, у которого нет `~/.ssh/config`. Рабочий вариант — без sudo,
   с адресом напрямую: сборка локально, копирование своим пользователем, активация через
   `--use-remote-sudo`.

Порт панели 2053 наружу не публикуется — панель доступна через nginx (`https://pubray1.zeroq.su/pubray/`
→ 200, `GET /` → 404 это норма). Проверка «`curl https://127.0.0.1:2053`» даёт `000` и ничего не значит.

**Откат** = строка `v3.10.2` + rebuild **и** восстановление `db/` из бэкапа: миграции v3.11.0 необратимы.
