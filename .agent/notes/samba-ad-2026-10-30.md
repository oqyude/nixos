## 1. Исследование (по исходникам, а не по памяти)

### 1.1 Какие опции `services.samba` дают AD DC в нашем пине — **никакие**

Источник: `$(nix eval --impure --raw --expr '(builtins.getFlake "/etc/nixos").inputs.nixpkgs.outPath')`
→ `/nix/store/sxb2ijsbdhi8s1lvc6ph692nm84vms3y-source`
→ `nixos/modules/services/network-filesystems/samba.nix`

Полный набор опций модуля: `enable`, `package`, `openFirewall`, `smbd.*`,
`nmbd.*`, `winbindd.*`, `usershares.*`, `nsswins`, `settings`.

Отсутствуют полностью:

| Ожидаемая опция | Статус в пине `31ecbaca` |
|---|---|
| `services.samba.enableActiveDirectoryDomainController` | **отсутствует** |
| `services.samba.domainName` | **отсутствует** |
| `services.samba.realm` | **отсутствует** |
| `services.samba.serverRole` | **отсутствует** |

Единственное, что похоже на AD: `services.samba.settings.global.security`,
который принимает `"ads"` — это **вход в существующий домен как member
server** (нужен рабочий AD DC), а не «быть» контроллером домена.

`nixos/modules/services/networking/samba.nix` в этом пине вообще не
существует — путь `services/networking/` не содержит samba; samba лежит в
`services/network-filesystems/`.

**Вывод:** «просто включить AD DC опцией nixpkgs» невозможно. Нужен
собственный модуль поверх `samba-tool`.

### 1.2 Пакет: почему текущий samba не может быть DC

`pkgs/servers/samba/4.x.nix` (пин):

```nix
enableLDAP ? false,            # → "--without-ldap --without-ads"
enableDomainController ? false, # → "--without-ad-dc"
```

`pkgs/top-level/all-packages.nix`:

```nix
samba4     = callPackage ../servers/samba/4.x.nix { };
samba      = samba4;                       # без ldap, без ad-dc
samba4Full = lowPrio (samba4.override {   # ldap + ad-dc, но заодно
  enableLDAP = true; enablePrinting = true; enableMDNS = true;
  enableDomainController = true; enableRegedit = true;
  enableCephFS = !isAarch64;              #   cups + avahi + ceph
});
```

Проверка на **живом** хосте — файл-сервер, который сейчас работает:

```
$ ls /nix/store/v6f7j8zxpimzs8rqrlgxskv9sk5v0y9a-samba-4.23.10/bin/ | grep samba-tool
(пусто)
```

То есть в `pkgs.samba` **нет бинаря `samba-tool` вообще** — провижинить домен
чем-то из текущего замыкания невозможно. И этот же `pkgs.samba` не может и
зайти в домен как member server (нет LDAP/ADS).

**Решение в модуле:** собственный минимальный override

```nix
sambaPkg = pkgs.samba4.override {
  enableLDAP = true;          # иначе --without-ldap --without-ads
  enableDomainController = true; # иначе --without-ad-dc
};
```

`pkgs.samba4Full` не взят намеренно: он тянет cups, avahi и cephfs ради
фич, которых AD DC не требует. Наш override даёт отдельный store-путь
(`/nix/store/1ndb6vfsc1dlxx7zz6lrqvph4rr3w3yb-samba-4.23.10`) и не трогает
файловый сервер.

### 1.3 Что делает `samba-tool domain provision` и что из этого делает NixOS

Источник: исходники samba 4.23.10 (`samba-4.23.10.tar.gz` из стора),
`python/samba/netcmd/domain/provision.py` и `python/samba/provision/__init__.py`.

`samba-tool domain provision` (неинтерактивный режим):

* **`realm` берётся из smb.conf, переданного через `-s`.** Флага `--realm` в
  списке опций команды **нет** (`provision.py`, `run()`:
  `realm = sambaopts._lp.get('realm')`, иначе `CommandError("No realm set!")`).
* пишет `<targetdir>/etc/smb.conf` с:
  `netbios name`, `workgroup` (= NetBIOS-имя домена), `realm`,
  `server role = active directory domain controller`,
  `private dir`, `lock dir`, `state directory`, `cache directory`,
  `binddns dir` и секциями
  `[sysvol] path = <state directory>/sysvol` и
  `[netlogon] path = <state directory>/sysvol/<realm>/scripts`;
* создаёт `<targetdir>/private/` — `sam.ldb`, `secrets.ldb`, `idmap.ldb`,
  `privilege.ldb`, `share.ldb`, `krb5.conf`, `kdc.conf`, `tls/`,
  `encrypted_secrets.key` (режим 0700);
* создаёт `<targetdir>/state/sysvol/` и каталог netlogon-скриптов;
* создаёт `<targetdir>/bind-dns/` с файлами AD-зон;
* заполняет `sam.ldb` схемой, SPN, SRV-записями, DNS-зоной (если
  `--dns-backend=SAMBA_INTERNAL`) и создаёт дефолтные GPO.

**Что делает NixOS за нас:** только приготовить состояние (каталоги, шаблон
smb.conf, systemd-юниты, пароль из sops). Сам провижининг — это вызов
`samba-tool`, который мы делаем в oneshot-юните.

**Два жёстких требования, вытекающие из исходников samba:**

1. **Шейры `[sysvol]` и `[netlogon]` обязательны.**
   ```python
   paths.sysvol  = lp.get("path", "sysvol")
   paths.netlogon = lp.get("path", "netlogon")
   ```
   Второй аргумент `lp.get()` — это **имя шейры**, а не значение по
   умолчанию. Проверено эмпирически на собранном samba 4.23.10:
   ```
   lp.get('path')             -> ''
   lp.get('path','sysvol')    -> '/…/state/sysvol'
   lp.get('path','netlogon')  -> '/…/state/sysvol/ad.zeroq.su/scripts'
   lp.get('path','nosuch')    -> None
   ```
   Если секции нет → `None` → `MissingShareError` → провижининг падает.
   *Именно поэтому в модуле smb.conf — шаблон, а не пустой файл.*

2. **Непустой smb.conf не перезаписывается.**
   ```python
   # only install a new smb.conf if there isn't one there already
   ```
   То есть наш шаблон выживает как есть — а именно так в нём задаются
   `dns forwarder`, `dns port` и `server services`. Если бы мы позволили
   samba сгенерировать smb.conf, эти три вещи молча получили бы чужие
   значения (`dns forwarder` — из `/etc/resolv.conf`, `server services` —
   дефолтный, с DNS на 53).

**Идемпотентность.** `samba-tool domain provision` на существующем домене
**не идемпотентен** — он падает на существующем `sam.ldb`. Идемпотентность
сделана в юните: если `<state>/private/sam.ldb` существует → «уже создано»,
`exit 0`. Повторный `systemctl start samba-ad-provision.service` домен не
перепровижинивает.

**Про `--dns-forwarder`.** У `samba-tool domain provision` **нет** флага
`--dns-forwarder` (в `run()` параметр есть, но опции нет — CLI его не
заполняет). Поэтому форвардер задаётся **в smb.conf** как `dns forwarder = …`,
что модуль и делает.

### 1.4 DNS: AD DC поднимает свой DNS на 53 — это конфликт, а не мелочь

* Внутренний DNS samba (`source4/dns_server/dns_server.c:727,740`) вешается на
  `lpcfg_dns_port(lp_ctx)`, то есть на smb.conf-параметр `dns port`
  (дефолт 53), на **каждом** интерфейсе, **UDP и TCP**.
* `server services` по умолчанию (`lib/param/loadparm.c:2845`):
  `s3fs rpc nbt wrepl ldap cldap kdc drepl ft_scanner winbindd ntp_signd kcc dnsupdate dns`
  — «dns» в списке, значит DC поднимает DNS сам.
* Список `server services` — P_LIST: элемент с префиксом `-` **удаляет**
  сервис (`lib/param/loadparm.c:1716-1745`). Поэтому `--dns-backend=NONE`
  даёт `server services = -dns`, и DNS не поднимается вовсе.
* На sapphira **53 уже занят coredns** (`coredns.service`, активен, зоны
  `zeroq.su` и `home.arpa`; `ss -ltnp` → `coredns`, pid 1039, `*:53`).

Это не «предупреждение», а невозможность: один порт — один владелец.
И цена конфликта асимметрична: coredns отдаёт **все** `*.zeroq.su` и
`home.arpa` для домашней сети (nextcloud, gitea, immich, authelia,
vtimeline, onlyoffice, …). Остановить coredns ради AD DC — значит уронить
весь внутренний DNS флотов.

### 1.5 Kerberos (88/464), LDAP (389/636), SMB (445)

| Порт | Кто слушает в AD DC | Свободен ли сейчас на sapphira |
|---|---|---|
| 88/tcp+udp | KDC (heimdal) | да |
| 464/tcp+udp | kpasswd | да |
| 389/tcp+udp | LDAP | да |
| 636/tcp | LDAPS | да |
| 445/tcp | SMB — **нужен DC для sysvol** | **НЕТ, держит `smbd` (файловый сервер)** |
| 135/tcp+udp | RPC endpoint mapper | да |
| 3268/tcp | Global Catalog | да |
| 137/138/139 | NetBIOS (nbt) | **НЕТ, держит `nmbd`/`smbd` файлового сервера** |
| 49152+ | dynamic RPC | да |

* **SMB 445 — жёсткое требование DC.** sysvol раздаётся по SMB; без этого не
  работает групповая политика. Отключить `smb` у DC нельзя.
* Значит DC и файловый samba **не могут сосуществовать на одном хосте**:
  оба занимают 445. Это и есть второй конфликт.
* LDAP/LDAPS/KDC/kpasswd/GC на sapphira свободны — с ними проблем нет.

### 1.6 Время

AD требует расхождение часов между DC и клиентами **≤ 5 минут** (иначе не
работают Kerberos-билеты, GPO, репликация).

На sapphira `chronyd` активен (`services.chrony.enable = true`,
`modules/server/chrony.nix`), и расхождение сейчас:

```
$ chronyc tracking
Reference ID    : 5D5F6442 (unspecified.mtw.ru)
Stratum         : 3
System time     : 0.000457176 seconds fast of NTP time
Last offset     : +0.000081992 seconds
```

**≈0.5 мс** против NTP — на три порядка лучше требования. Время — не
блокер. Отдельного внимания требует только то, что *все* участники домена
(включая будущие клиенты и второй DC) должны быть синхронизированы с одним
источником.

### 1.7 Пароль администратора

* Только через sops: `config.sops.secrets.<name>.path`. В Nix-конфиге, в
  сторе и в git — **никогда**.
* Модуль **читает** файл в рантайме (юнит `samba-ad-provision.service`), в
  конфиг NixOS пароль не попадает.
* Assertion запрещает путь внутри `/nix/store` (пароль в сторе читается всеми
  и оседает в истории git).
* Требования samba: минимум **7 символов** (`DEFAULT_MIN_PWD_LENGTH`) и
  качество (`samba.check_password_quality` — 3 из 4 классов символов:
  заглавная, строчная, цифра, спецсимвол).
* **Документированное ограничение:** `samba-tool` умеет получить пароль
  только через `--adminpass=`, т.е. пароль попадает в `argv` и читается через
  `/proc/<pid>/cmdline` на время провижининга (несколько минут, один раз).
  Интерактивный режим `samba-tool domain provision` помочь не может: он
  включается только при **полном отсутствии** аргументов
  (`if not self.raw_argv: interactive = True`), а `--targetdir` без аргументов
  не подать — да и `smb.conf` тогда взялся бы из `/etc/samba/smb.conf`
  (чужой). На хосте с двумя пользователями (root + oqyude) и `/proc` в
  обычном режиме это окно приемлемо; если владелец хочет нулевой риск —
  вариант «провижинить один раз руками, а Nix только держит рантайм-юнит».
  Второй митиг — после провижининга сменить пароль Administrator.

## 3. Решение по каждому конфликту

### 3.1 Конфликт 53 (DNS)

**Реализовано: assertion.** Модуль не даёт включить AD DC с DNS на 53, пока
`services.coredns.enable` включён:

```nix
assertion = cfg.dnsBackend != "SAMBA_INTERNAL" || cfg.dnsPort != 53
             || !config.services.coredns.enable;
```

Три документированных выхода (выбирает владелец):

1. **Отдельный хост для DC (рекомендуется).** 53 там свободен, AD DC
   владеет своей зоной, coredns не трогаем. Единственный вариант, при
   котором AD DC получается полноценным.
2. **`dnsBackend = "NONE"`** — DC не поднимает DNS (`server services = -dns`),
   порт 53 не трогается. **Цена:** AD-зоны (`ad.zeroq.su`, SRV-записи
   `_ldap._tcp`, `_kerberos._udp`, `_kpasswd._tcp`) не создаются и не
   обслуживаются → ни один клиент не сможет ввести домен, GPO и Kerberos
   не заработают. Годится только как «DC без DNS».
3. **`dnsPort = 5353`** — AD DNS уходит с 53 (это реальный smb.conf-параметр,
   см. §1.4). **Цена:** AD-клиенты ждут DNS на 53 → coredns должен
   пересылать AD-зоны на 127.0.0.1:5353. Технически возможно (в coredns
   нужны явные зоны под SRV-имена), но это ручная и хрупкая конструкция,
   которую надо проектировать отдельно.

### 3.2 Конфликт 445 (SMB)

**Реализовано: assertion.**

```nix
assertion = !(config.services.samba.enable && config.services.samba.smbd.enable);
```

Два выхода:

1. **Отдельный хост для DC** — DC и файловый сервер на разных машинах.
   Файловый samba на sapphira продолжает работать как сейчас.
2. **Выключить файловый сервер на этом хосте** (`services.samba.enable =
   false`) и раздавать шары из smb.conf самого DC. Тогда шары `nixos`,
   `root`, `oqyude` надо перенести в smb.conf DC (в наш шаблон их сейчас
   нет) — это отдельная правка.

**Побочная находка (исправлена в этом же коммите).** Пока я доказывал
сценарий «файловый сервер выключен», выяснилось, что `modules/server/samba.nix`
описывал `systemd.services."samba-smbd"` **вне** `services.samba.enable`.
При `services.samba.enable = false` nixpkgs-юнит (с `ExecStart`) исчезал, а
наш `unitConfig` оставался → в системе появлялся **фантомный юнит без
ExecStart** — ровно та ловушка, что описана в ADR-0004 / R1.14 («Service has
no ExecStart=… Refusing.»). Исправлено: юнит теперь создаётся под
`lib.mkIf config.services.samba.enable`. Для работающих хостов (`enable =
true`) поведение не меняется **ни на байт** — меняется только случай
«файловый сервер выключен», которого раньше просто не существовало.

### 3.3 Прочие требования (не конфликты, но документированные)

* **Время** — не блокер (§1.6), но все участники домена должны быть
  синхронизированы с одним источником.
* **Пароль** — только sops (§1.7).
* **Имя домена** — не угадывается, assertion требует явного `realm` или
  `dnsDomain`.
* **Файрвол** — `openFirewall = false` по умолчанию: на этом флоте файрволом
  является роутер (`firewall.enable = false` — намеренно, инвариант 3
  проекта). Опция есть, если владелец перейдёт на software-файрвол.
* **Хранилище** — база DC лежит в `/var/lib/samba-ad` (локально), а **не** на
  внешнем диске через `xlib.helpers.mkServiceStorage`. База контроллера
  домена не должна лежать на USB/exFAT-томе, который можно выдернуть, и
  монтирование guard'а здесь не нужен.

## 4. Модуль `modules/server/samba-ad.nix`

Опции (все — под `host.samba-ad`, объявлены в самом модуле, как
`host.ssh.enable` в `modules/essentials/ssh.nix`; в `modules/options.nix`
попадают только опции, которые **устанавливает** один модуль, а **читает**
другой):

| Опция | Тип | Дефолт | Смысл |
|---|---|---|---|
| `enable` | bool | **`false`** | включить DC |
| `domainName` | str | `"ad"` | NetBIOS-имя домена (`workgroup`) |
| `realm` | null\|str | `null` | Kerberos realm, напр. `AD.ZEROQ.SU` |
| `dnsDomain` | null\|str | `null` | AD DNS-зона, напр. `ad.zeroq.su` |
| `adminPasswordFile` | null\|path | `null` | путь к sops-секрету с паролем |
| `dnsForwarder` | null\|str | `null` | верхний резолвер для AD DNS |
| `dnsBackend` | enum | `"SAMBA_INTERNAL"` | `"SAMBA_INTERNAL"` \| `"NONE"` |
| `dnsPort` | port | `53` | порт встроенного AD DNS |
| `openFirewall` | bool | `false` | открыть порты в файрволе NixOS |

`realm` и `dnsDomain` — два вида одного: задать можно любой один, второй
выводится (`realm` = upper(dnsDomain), `dnsDomain` = lower(realm)).

**Что модуль НЕ делает при `enable = false`:** не добавляет ни одного юнита,
ни одного порта, ни одного пакета, ни одного файла в замыкание. Это
проверено (§5.2).

**Юниты при `enable = true`:**

* `samba-ad-provision.service` — `Type=oneshot`, `RemainAfterExit=true`,
  идемпотентный (по наличию `private/sam.ldb`), `After/Wants
  sops-nix.service`, `TimeoutStartSec=30min`, `WorkingDirectory=/var/lib/samba-ad`.
  Скрипт: читает пароль из файла в рантайме, кладёт шаблон smb.conf в
  `state/etc/`, вызывает `samba-tool domain provision --realm=… --domain=…
  --server-role=dc --dns-backend=… --targetdir=/var/lib/samba-ad
  --use-rfc2307 --adminpass=… -s /var/lib/samba-ad/etc/smb.conf`.
* `samba-ad.service` — `Type=notify` (samba умеет sd_notify через
  `lib/util/become_daemon.c`, как в upstream-ном `samba.service`),
  `ExecStart = <samba>/sbin/samba --foreground --no-process-group -s
  /var/lib/samba-ad/etc/smb.conf`, `Requires=samba-ad-provision.service`.

## 6. Что остаётся решением владельца

1. **Нужен ли AD DC вообще.** Домашний флот из 6 машин + телефон; домен
   Windows — это операционная нагрузка (KDC, репликация, sysvol, бэкапы
   базы `sam.ldb`, синхронизация времени, AD DNS). Если задача — «проверить,
   что AD DS в принципе поднимается», то достаточно одного эксперимента на
   отдельной машине; если задача — «домен для домашних Windows-машин»,
   решение отдельное и требует плана на 2+ DC.
2. **Имя домена и realm.** Предложение: NetBIOS `AD`, realm `AD.ZEROQ.SU`,
   AD DNS-зона `ad.zeroq.su` (подзона `zeroq.su`, а не сама `zeroq.su` —
   чтобы не отбирать зону у coredns). Это предложение, а не навязывание:
   опции по умолчанию `realm = null`, и без явного значения модуль откажется
   собираться (assertion).
3. **Где живёт DC.** На sapphira — **не рекомендуется**: 2 vCPU / 5.6 GB и
   ~20 сервисов; DC требует стабильного ресурса. Разумные варианты:
   новая NixOS-конфигурация (например `vdc`) на отдельной машине;
   либо существующий хост, выбранный владельцем.
4. **Делегирование DNS.** Если DC на отдельном хосте — нужен переход зоны
   `ad.zeroq.su` (или SRV-зон) с coredns на AD DNS, либо AD DNS с
   `dns forwarder` на coredns. Если DC на sapphira — см. §3.1 (три варианта
   и их цена).
5. **Пароль администратора.** Владелец создаёт sops-секрет
   (`secrets/samba-ad-admin.yaml`, `format = "binary"`, 7+ символов, 3 из 4
   классов) и прописывает `host.samba-ad.adminPasswordFile =
   config.sops.secrets.samba-ad-admin.path;`. В конфиг и в git пароль не
   попадает.
6. **Файловый samba на sapphira.** Если DC встаёт на sapphira — файловый
   сервер там придётся выключить (или перенести шары в smb.conf DC). Если DC
   на отдельном хосте — файловый samba остаётся как есть.
7. **Роль файлового samba как member server.** Сейчас он собран без
   LDAP/ADS (`pkgs.samba`), то есть зайти в домен не может. Если задача —
   «шары sapphira видны доменным клиентам», нужен `pkgs.samba4` с
   `enableLDAP = true` и `security = ads` + `realm` + `netbios name`.
   Это отдельная работа, в этот модуль не входит.

## 8. Что НЕ сделано / ограничения

* **Домен не создан**, DNS не переключён, ни один работающий сервис не
  тронут. `nixos-rebuild` не запускался.
* **Пакет с AD DC не собран** — `nix build --dry-run` показывает его в
  плане, но сборка `samba` с `enableLDAP/enableDomainController` на 2 vCPU
  займёт долго; для доказательства достаточно было оценки конфигурации.
* **Ни один provisioning не запускался** — поведение `samba-tool domain
  provision` на этой машине не проверялось. Все утверждения о нём взяты из
  исходников samba 4.23.10 и из эмпирической проверки `lp.get()` на
  собранном samba.
* **Путь `sbin/samba` и `bin/samba-tool`** в собранном AD-варианте samba
  выведен из системы сборки samba (`SAMBA_BINARY` → `SBINDIR`,
  `SAMBA_SCRIPT` → `BINDIR`) и из уже собранного `pkgs.samba`
  (`bin/` и `sbin/`). Первую сборку стоит перепроверить:
  `ls $(nix eval --raw .#…sambaAd.outPath)/{bin,sbin}`.
* **`Type=notify`** у `samba-ad.service` взят из upstream-ного
  `samba.service`; если бы конкретная сборка samba не отправляла
  READY=1, юнит упал бы по таймауту — это проверяется первым же
  `systemctl start` после включения.
* **Шары `nixos` / `root` / `oqyude`** в smb.conf DC не перенесены — они
  остались у файлового сервера. Перенос нужен только если DC встаёт на
  sapphira.
* **Резервное копирование `sam.ldb`** не организовано. Для DC это
  обязательно (потеря базы = потеря домена), и это отдельная задача.
